# JetCode Platform — что сделано

Платформа «Claude Code как сервис»: клиент оплачивает тариф, создаёт проект,
привязывает свой Claude Pro/Max аккаунт и работает с Claude Code через чат
LibreChat — за кулисами каждый чат живёт в собственной tmux-сессии на сервере.

Состоит из двух репозиториев:

- **jetcodem** — платформа (Laravel 12 / PHP 8.4, PostgreSQL 16, tmux, Claude Code CLI);
- **этот форк LibreChat** (ветка `codex/librechat-v2-staging` поверх `dstlab-billing`) —
  UI, биллинг и интеграционные хуки.

## Поток клиента

```
/billing  →  оплата тарифа (= слот на один проект)
сайт      →  New Project (проект платформы: каталог, состояние AWAITING_CREDENTIAL)
/billing/claude → «Привязать аккаунт» → OAuth-ссылка → код → проект READY
сайт      →  проект появился моделью в эндпоинте JetCode → чат работает
             от лимитов ЕГО подписки, в ЕГО tmux-сессии
```

## Сделано по пунктам

### 1. Доменное ядро (jetcodem)
- Схема: `users` (+ `linux_uid`/`linux_login`), `subscriptions` (слоты),
  `projects` (id `p_<hex>` — непрозрачный и неизменяемый, попадает в путь),
  `credentials` (токен только в vault, в БД лишь путь), `chats` (id `c_<hex>`
  = имя tmux-сессии), `chat_sessions` (история привязок), `chat_runtime`
  (эфемерный), `credential_link_sessions`, `usage_events`, `audit_log`.
- Инварианты держит **база**: `UNIQUE(projects.subscription_id)` — одна
  подписка платит за один проект; частичный уникальный индекс
  `one_live_chat_per_project` — один живой чат на проект (двойной клик
  проигрывает в Postgres, не в UI).
- Привязка `chat → claude_session_id` — **скользящая**: идемпотентный upsert
  на каждый SessionStart (`/clear` и баги `--resume` двигают указатель,
  история не сиротеет).
- State-machines: чат `CREATED→STARTING→LIVE⇄IDLE→SUSPENDED→…`, проект
  `PROVISIONING→AWAITING_CREDENTIAL→READY⇄SUSPENDED→ARCHIVED`, подписка
  с каскадами на проект и чаты.

### 2. Биллинг → платформа
- Оплата заказа (идемпотентная точка `creditOrder`) зовёт
  `POST /internal/billing/paid`: user + Linux-идентичность + подписка-слот.
  Идемпотентно по `order_id`, недоставка ретраится поллером.
- Тарифы апстрима = подписки с `durationDays`; интеграция пережила мёрж.

### 3. Создание проекта из UI
- Кнопка New Project в LibreChat → `POST /internal/projects` → потребляет
  старейший свободный слот → каталог, состояние AWAITING_CREDENTIAL.
- Нет слота → UI-проект **откатывается**, клиент видит «оплатите тариф»
  (раньше молча появлялся проект-пустышка).
- Страница `/billing/claude` всегда показывает счётчик свободных слотов.

### 4. Привязка клиентского Claude-аккаунта (поток A2)
- «Привязать аккаунт» → платформа запускает `claude setup-token` в скрытой
  tmux-сессии, перехватывает OAuth-URL из pane, клиент вводит код на сайте,
  годовой токен ложится файлом 0600 в vault-каталог → проект READY.
- Клиент не видит терминал; платформа не видит пароль. Ретрай кнопки
  идемпотентен (та же ссылка), TTL 5 минут, ошибки с содержимым pane
  в диагностике.

### 5. Мост LibreChat ↔ платформа
- OpenAI-совместимый эндпоинт `/v1` (bearer-ключ): `models` = READY-проекты
  **только этого пользователя** (email в заголовке через
  `{{LIBRECHAT_USER_EMAIL}}`), `jetcode` — стабильный алиас «мой текущий
  проект». Chat completions + минимальный SSE.
- В выборе провайдера один JetCode: встроенные эндпоинты выключены
  (`ENDPOINTS=custom`), примеры из конфига удалены, генерация заголовков
  отключена (экономит полный прогон claude на разговор).

### 6. Runtime: tmux + Claude Code
- Чат = tmux-сессия `c_<id>` в каталоге проекта с его `CLAUDE_CONFIG_DIR`
  (анти-гонки), `CLAUDE_CODE_PROJECT_DIR_NAME` (история переживает переезд)
  и токеном клиента в env; pane-pid пишется в `chat_runtime`.
- **Персистентный пайплайн**: pane-команда сессии — долгоживущий
  `claude -p --input-format stream-json --output-format stream-json`
  (+`--resume`); сообщения через FIFO, ответы из журнала событий.
  Задержка сообщения: с ~4–5 с (холодный CLI-старт) до ~1.5–2 с (чистое
  API-время). Любой сбой пайплайна прозрачно падает на one-shot `claude -p`.
- Hook `SessionStart` в конфиге каждого чата репортит session_id платформе.
- Самолечение: рестарт контейнера (tmux умирает, БД говорит LIVE) чинится
  на следующем сообщении; занятый слот = **вытеснение** держателя
  (SUSPENDED, данные целы), а не ошибка.

### 7. Отлаженные вживую грабли (все закреплены тестами/фиксами)
- дедлок single-thread PHP-сервера с hook-коллбэком → 8 воркеров `php -S`
  напрямую (artisan serve режет env — из-за этого же терялся HOME);
- tmux SIGHUP'ит pane, когда и stdout и stderr уходят с pty;
- `fopen(fifo,'a')` виснет навечно без читателя (`r+` не блокируется);
- TUI глотает Enter, приклеенный к вставленному коду (send-keys `-l`,
  пауза, отдельный Enter);
- `setup-token` печатает токен и мгновенно выходит — `remain-on-exit`;
- перенос OAuth-URL на 80-й колонке pane (детачед-сессии 500×100);
- гонка «сообщение + генерация заголовка» плодила FAILED-чат, в который
  затем маршрутизировались сообщения.

### 8. Инфраструктура
- Стек v2 (`docker-compose.v2.yml`) полностью изолирован от боевого
  LibreChat: свои имена контейнеров, тома, Traefik-роутеры; ingress через
  общий edge-network, наружу порты не публикуются.
- Платформа (`docker-compose.app.yml`): php-контейнер с tmux и Claude Code
  CLI + свой Postgres 16, только во внутренней сети LibreChat v2.
- Тесты: **99 passed** на PostgreSQL 16 и настоящем tmux
  (`docker-compose.test.yml`); фикстуры эмулируют one-shot и stream-json
  режимы claude, включая баг ротации id при resume.

## Что осталось (следующие шаги)
- Токен-стриминг в UI (`--include-partial-messages` → настоящий SSE).
- Чат платформы на разговор LibreChat (сейчас один активный чат на проект).
- Реальный root-провижинер (useradd/linger/квоты) за готовым интерфейсом
  `UserProvisioner`; systemd slice/scope-лимиты.
- Терминал-гейтвей (attach к tmux из браузера по одноразовым тикетам).
- Vault вместо файлового хранилища токенов; телеметрия расхода в
  `usage_events`.

# LiteLLM pricing discovery: virtual key, name-based detection, all-or-nothing precedence

LibreChat needed automatic pricing for LiteLLM proxy endpoints, previously supported only for OpenRouter/Helicone. Three choices here are easy to get wrong in the opposite direction and hard to unwind once admins depend on the behavior:

**Virtual key over master key.** We call `/model/info` with the endpoint's own configured (virtual) key rather than requiring the proxy's admin/master key. Verified against LiteLLM source (`litellm/proxy/proxy_server.py`, tags `v1.87.0` and `v1.93.0`): the route is declared `dependencies=[Depends(user_api_key_auth)]` — the same generic auth used by ordinary completion routes, not an admin-only dependency — so this isn't a permission workaround, it's the route's actual design. A 401/403 is still possible for other reasons (a key scoped away from a given model, an older LiteLLM version predating this route), which is why the fetch still degrades gracefully rather than assuming success. The alternative — requiring a master key — would mean every self-hosted LibreChat admin has to hand a secret with proxy-wide admin rights to a single per-endpoint config field, for a feature that's supposed to reduce risk (mispricing), not add to it.

**Name-based detection, not an explicit flag.** Naming a custom endpoint `LiteLLM` (case-insensitive) activates the fetch, mirroring the existing `KnownEndpoints`/`FetchTokenConfig` convention for OpenRouter/Helicone. An explicit opt-in field would be more discoverable but would be the only place this codebase does it that way — every other automatic-pricing endpoint works by name, and a second convention living alongside the first is a worse trade than one convention with (the same) quirk.

**All-or-nothing precedence with static `tokenConfig`.** Any static override present on an endpoint disables the automatic fetch entirely, for every model on that endpoint — not merged per-model. This matches the pre-existing OpenRouter/Helicone behavior exactly. Per-model merge would be more convenient for the one-alias-needs-pinning case, but it means an admin can no longer read "this endpoint has a `tokenConfig` block" as "this endpoint's pricing is fully pinned" — a silent, partial dependency on network fetch would need to be re-discovered by whoever debugs a future rate discrepancy.

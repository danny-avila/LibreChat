# Media retention and native conversation consumers

Submission and import admission persist `publicationExpiresAt`. A timestamp fixes the presentation deadline before publication can be interrupted; `null` records an explicitly permanent presentation. Recovery preserves that decision. Older staged submissions without the field use the configured publication retention interval, anchored to their original creation time.

Native recordings have two independent consumers: their Studio presentation and registered conversation IDs. Deleting the presentation does not invalidate a saved source chat or fork. Removing the source conversation also retires its linked presentation. A fork keeps the immutable native parts and generated originals until the final conversation consumer is released. The original source deadline is a hard ceiling, including for forks. Native image files use one job retainer for these consumers, so additional conversation consumers do not consume additional File retainer slots.

The host registers a new local clone's native references before publishing the clone. Registration is bounded by the existing native part and retainer limits. If publishing a new clone fails, the host releases that new conversation's consumers. Cross-account or cross-deployment imports detach private native identities instead of registering them.

Legacy native jobs have no consumer list. `migrateMediaNativeConsumers` discovers their references in owned, unexpired saved Messages and registers each conversation once. Only an in-progress invocation may retain an unsaved source. Migration runs before destructive transitions and in background cleanup. A stored consumer population above the configured limit raises a capacity error and preserves its payload; raising the existing retainer limit allows the same migration to resume. Cleanup must report this failure instead of treating a zero-progress pass as completion. The deployment must upgrade its writers before enabling native media, as described in the main design.

Retirement waits for terminal provider state and completed accounting. It then erases presentation titles, prompts, and import payloads. Native job payloads survive while registered conversations need them. After the final consumer, an atomic `purging` fence rejects new registrations before private native parts and job payloads are erased and the original File retainer is released. A durable cleanup flag repairs interruption between consumer release and retirement. Submission fingerprints, receipts, accounting records, and storage tombstones remain available for replay and reconciliation; public Files queries exclude unavailable tombstones.

Credit admission first records an unfunded settlement, then obtains a separate accounting grant on the existing owner fence. Cancelling a queued job does not remove that accounting grant. Recovery can close an unfunded receipt without charging it; the initializer's original Mongo receipt identity prevents a delayed write from using a replacement receipt. Every media balance mutation also checks the balance generation, including a persisted generation assigned to legacy balances before use. Deleting and recreating the same balance ID therefore cannot restore an old allocation. Debt collection uses the same owner admission rule.

Account deletion keeps its permanent owner fence after the User document disappears. Normal completion and background recovery share accounting cleanup, and real balance holds or pending settlements prevent that cleanup. Repeated sweeps reclaim acknowledged receipts, abandoned unfunded admissions, unstarted debt collection, and late default balance or media ledger rows left by requests that were already in progress. This is the same delayed-write cleanup model used for Files; closing a receipt prevents those delayed requests from restoring a funded hold. Completed outputs and their recorded usage can finish publication locally after a provider credential is removed, without another provider submission, poll, or download.

File cleanup reuses the existing deletion attempt counter, retry deadline, and host retry policy. Asset-write cleanup has equivalent scoped bookkeeping for its separate collection. Persisted retry deadlines prevent a failed oldest object from occupying every bounded cleanup page.

The thread detail API returns turns newest first with a descending sequence cursor. It also supplies `latestImageContext`, selected independently of the visible page from the newest successful image or imported original that remains available. Failed turns and expired images do not hide an older usable image. Original generation parameters are projected from already-loaded job records, including for turns saved before this change.

Native replay batches authorize parts against the requesting owner, tenant, model, credential binding, consumer, source deadline, and current canonical File state. New text-only transcripts require two database reads per batch. Older records additionally verify saved references until migration completes; image batches validate their originals in one shared File query.

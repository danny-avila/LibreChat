# Media generation: frontend integration research

Research date: 2026-09-15. This document describes inspected code and a proposed design; it does not implement the feature. Paths identified as proposed do not exist yet. Provider availability and API details belong in the companion provider research.

## Recommendation

Make chat and a dedicated studio equal first-class entry points to the same media threads, generation jobs, and assets. The requested studio experience is concrete: a **Media Studio sidebar button**, a model selector for image/video generation and uploaded-image editing, the ability to queue multiple jobs, and a **tile grid where each tile is a thread for iteration**. A person should also be able to generate and refine media directly in chat, open its thread in the studio, and bring a selected revision into an existing or new conversation. The first usable delivery should demonstrate that round trip.

Use a full authenticated route for the studio, with a persistent sidebar entry, and compose shared media controls and result presentation into chat. Keep the current conversational workflow available. Gemini's native text-and-image generation should render ordered text and image results as model output; it should not require a second model to invoke an image tool. Tool-driven generation remains a supported way to reach the same media service.

One tile represents one durable `MediaThread`. A thread contains turns/revisions, one or more generation jobs, and resulting assets; a job is an execution within that thread. Multiple threads can have queued/running work simultaneously, and one thread can contain concurrent variants. The present image tool card is useful integration evidence, but it does not supply this thread identity, queue, multi-minute video lifecycle, refresh recovery, or revision history.

## Two entry points, one workflow

### Chat

Expose an explicit image/video generation action in the composer or model capabilities UI. A user can select the media-capable model, supply the prompt and valid references, and change a small set of operation-specific controls. Conversational agent use can still invoke media generation through a tool, but direct native generation must not depend on an orchestration agent.

For a native Gemini text-and-image response, keep the provider's ordered text/image parts in the conversation. For a video job, put a persistent run card into the conversation as soon as submission is accepted. The card references the same thread, revision, job, and assets shown in the studio, including after a page reload or when completion occurs after the text turn ends. This avoids keeping a chat connection open as the only owner of a video operation. A general chat may contain several independent media threads; do not equate `conversationId` with `threadId`.

Every media card should expose preview/play, download, open in studio, and reuse as input when the operation supports it. Present compact high-use controls in chat and a fuller parameter panel in the studio. Both surfaces must be able to submit, cancel, retry, and inspect results without making the other route mandatory. A chat message remains anchored to its chosen revision: iterating the studio thread must not replace an image in an older message merely because the tile cover changes.

### Studio

Proposed URLs: `/studio` for the thread grid and `/studio/threads/:threadId` for thread detail, with optional revision/job selection by stable ID. A deep link to a job should resolve its owning thread. These are design suggestions, not implemented routes. Keep URL state limited to identifiers and non-sensitive filters; do not put a private prompt or provider credential into the address bar.

The workspace starts with model/operation selection, a prompt and reference uploader, and a paginated **thread tile grid**. Visible entry actions cover a new image, a new video, and editing an uploaded image. The selected operation filters the model choices and valid controls. Uploading an image establishes an authorized source/reference in the new thread; it does not require generating an image first. After submitting one job, the user can immediately prepare and queue another thread or a valid independent variant in an existing thread. One busy tile must not disable the entire studio.

Each tile shows a stable thread title/identity, a selected successful image or video poster when available, active/queued job counts, and an indication that a new result or failed attempt needs attention. A first queued generation can show a placeholder cover without pretending an asset already exists. Opening the tile shows ordered turns, the revision/variant history, job-specific status, a selected result, and a refinement composer. The user selects a result/input revision and submits a change in that same thread. Returning to the grid preserves tile identity and selection even when jobs finish out of order.

On mobile, retain the tile workspace and make thread detail a focused route with a back-to-grid action; preserve the shared sidebar opener. A split desktop inspector is an optional presentation choice, not a second thread model. Full timeline editing, audio mixing, keyframes, and an NLE-style editor remain separate product scope.

The landing experience should distinguish an empty thread library, filters with no matches, configuration with no eligible providers, missing user credentials, denied access, and a failed fetch. The first two are normal empty states; configuration/access/fetch failures need their own explanations. A user without configuration privileges should not see an unusable administrative setup form.

### Thread identity, queue, and concurrent iteration

| Concept                 | UI and persistence meaning                                                                                                                                                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MediaThread`           | One durable creative workspace and one grid tile. Holds stable identity, owner/access, submitted turns/revisions, job/asset relations, selected cover, and provenance. It survives failed/cancelled attempts and can receive another turn later.                      |
| Turn/revision           | A submitted prompt or refinement with a stable parent revision, resolved input asset IDs, model/settings, and native continuation snapshot where applicable. Distinguish a revision's creation order from job completion order.                                       |
| Job                     | One accepted generation operation with its provider execution/attempt lifecycle. Queue/running/cancellation/retry state belongs here. One thread can have multiple jobs; one job can produce multiple candidate assets.                                               |
| Asset                   | A stored source image, output, or derivative. Opening, downloading, or choosing it for another operation does not create a paid generation.                                                                                                                           |
| Tile cover              | The thread's selected completed revision/asset, or an initial placeholder. A newer running/failed attempt does not replace a usable cover with an error. A late sibling completion must not silently change the user's selected revision; surface it as a new result. |
| Thread activity summary | Derived counts such as queued/running jobs plus actionable failures/new results. A thread is not permanently “failed” because one attempt failed, and a successful cover does not imply every job is finished.                                                        |
| Queue view              | An optional expanded list/filter of accepted jobs across threads, with their own actions and statuses. The tile grid itself already exposes queued work; a separate queue panel is not required to make the requested workflow usable.                                |

For example, three tiles can represent “Poster,” “Product photo,” and “Short clip.” The poster thread can run two lighting variants from revision 1 while a product-photo edit runs and two independent clip variants queue. That is **three threads and five jobs**, not five tiles. Asking one job for three output candidates is also different from queueing three independent jobs; the UI and usage estimate should preserve that distinction.

Every accepted job freezes an immutable parent/input snapshot. If two variants start from revision 1, both retain that parent even when one finishes first. Never resolve a queued job against “the thread's latest image” at execution time. Native multimodal continuation must branch from the captured provider context rather than allowing concurrent jobs to mutate a single session cursor. A follow-up requiring an unfinished output is not yet an independent runnable job: the initial UI should wait for a ready result, unless a later explicitly designed dependency queue supports that relation.

Use optimistic concurrency/revision checks for shared thread metadata such as cover selection and branching. Two tabs may create deliberate sibling revisions, but stale updates cannot overwrite the selected head/cover or duplicate a submission. Changing models preserves the thread's history and authorized references; provider-specific continuation transfers only where the API supports it.

Cancellation targets a job. Removing a tile/thread is a different destructive action that needs explicit behavior for its pending jobs, retained outputs, linked chat messages, and references. Hiding a completed tile is not evidence that its queued work was cancelled. Cover selection, status summaries, and queue observation must recover from durable records on refresh.

## Shared capability and presentation contracts

The server should return an authorized media catalog containing stable deployment/model identifiers, display names/provider identities, supported operations, input/output modalities, valid parameter values, constraints, availability, and credential/setup state. Show configured custom provider names. Separate deployment identity from provider family so two compatible gateways are not collapsed into one choice.

Use a typed common form for prompt, references, aspect ratio/size, quality, output count, duration, and audio where those fields apply. Add provider-specific typed extensions behind an advanced section when their semantics are different. Do not expose one universal slider that silently rounds, drops, or reinterprets its value when a provider changes. Model changes should preserve compatible values and visibly reset incompatible ones. Server validation is authoritative, and a stale catalog error should refresh capability data without discarding the draft.

The generation response should support:

- Stable thread, turn/revision, job, and output IDs, plus server versions, separate from provider task IDs. A thread-list response supplies bounded summaries/cover metadata without loading every turn and asset.
- Ordered output parts, including text and one or more media assets; independently available previews are not final output assets.
- An immutable snapshot of submitted operation/model/settings, parent revision, and resolved typed input asset references, with opaque server-owned continuation metadata where needed.
- Explicit progress phase and optional measured progress, output/asset status, recoverable error category, supported cancellation/retry actions, and creation/update timestamps.
- Optional price estimate/usage information only when the backend has a reliable basis. Unknown cost or duration must remain visibly unknown; existing token counts alone do not describe image/video billing.

Share a media run card, asset preview/player, capability-aware settings, input picker, refinement composer, and result actions between chat and studio. A studio thread tile composes cover and activity summary; thread detail composes the same run/result parts used in chat. Keep chat-specific message anchoring and studio-specific layout outside those components. Consider a shared generic preview/player primitive in `packages/client` only if both use sites need it; feature policy should remain in the media feature.

## State ownership and proposed module boundary

All paths in this tree are **proposed**, except the existing shared endpoint/key/type files identified below it:

```text
client/src/components/Media/
  host.tsx           # supplied auth/config/preferences/navigation/actions
  state.ts           # feature-owned Jotai drafts by thread and view state
  controls/          # operation/model/parameters/reference inputs
  display/           # run card, ordered results, image/video preview
  studio/            # thread tile grid, thread detail, optional queue filter
client/src/data-provider/Media/
  queries.ts         # catalog, thread summaries/detail, jobs and assets
  mutations.ts       # create thread, submit revision, cancel/retry job, reuse
```

New transport functions, endpoints, and query/mutation keys belong with the existing [data-service](../../../packages/data-provider/src/data-service.ts), [api-endpoints](../../../packages/data-provider/src/api-endpoints.ts), and [keys](../../../packages/data-provider/src/keys.ts) integration. ## Lifecycle and recovery requirements

| State/transition                   | User-visible behavior and contract                                                                                                                                                                                                                                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Catalog/permissions loading        | Keep a stable shell with labeled loading state. Disable generation until capabilities/authorization resolve; keep the prompt editable.                                                                                                                                                                                                          |
| Reference upload/validation        | Show individual progress and errors, allow removal/cancellation, and prevent submission with unresolved required inputs. Validate MIME, size, duration/dimensions, count, and input role against the selected operation.                                                                                                                        |
| Submitting                         | Disable duplicate submit for this attempt while retaining the prompt/settings. Use a stable client request identity so a timeout can be reconciled with the backend. Other threads and valid independent variants remain usable.                                                                                                                |
| Accepted/queued                    | Immediately display the persisted thread tile and job queue phase, or update an existing tile's counts for another job. Navigating away and submitting other work are permitted. Acknowledged jobs are not dependent on a mounted component.                                                                                                    |
| Running                            | Display server phase and genuine progress when available; otherwise use indeterminate status. Preview frames or partial images are labeled as previews. Do not infer failure from a quiet network connection.                                                                                                                                   |
| Importing/processing output        | Separate provider completion from assets becoming usable. Keep “preparing result” visible while durable storage/posters/thumbnails are produced.                                                                                                                                                                                                |
| Success/partial success            | Render every ready output in its own revision/job and mark new results on the thread tile. Preserve the selected cover during sibling completions. A failed thumbnail should not hide a downloadable original. Partial output failure identifies affected items without discarding successful assets.                                           |
| Provider/validation/policy failure | Preserve the draft and show a localized category and appropriate corrective action. Do not blindly retry validation failures or expose secrets/internal traces from provider responses.                                                                                                                                                         |
| Cancellation requested             | Show that a stop was requested, then the confirmed result. Some providers cannot stop work after acceptance; expose the actual supported action and consequences. Closing a view or aborting a fetch is not cancellation.                                                                                                                       |
| Cancellation races completion      | The server's terminal state wins. If assets completed before cancellation, show them; do not locally erase success because a stop button was clicked.                                                                                                                                                                                           |
| Retry                              | Retry only when the server knows another attempt is appropriate, or reconcile an uncertain submission first. Do not automatically resubmit expensive generation on component mount, focus, reconnect, or generic mutation retry.                                                                                                                |
| Offline/reconnect                  | Keep the last known state with a connection indicator. Re-fetch an authorized snapshot and resume updates; clear the indicator only after reconciliation.                                                                                                                                                                                       |
| Refresh/restored session           | Load thread summaries, selected detail/revision, and accepted job states; recover linked message cards. Deduplicate replayed events, ignore older server versions, and retain terminal state when older snapshots arrive. Do not confuse older creation-order revisions with stale event versions. A restored local draft never submits itself. |
| Model/credential/config changed    | Keep already-owned results browsable if permitted. Explain why the former model is unavailable for another run, refresh catalog/credentials, and require a deliberate replacement selection.                                                                                                                                                    |
| Expired/deleted/revoked asset      | Show a stable unavailable state and remaining provenance permitted by policy; remove invalid generation/reuse actions. Distinguish this from a transient download error.                                                                                                                                                                        |

Prefer a snapshot plus events contract with one deduplicated subscription per relevant scope, or a shared query poller with server-provided intervals/backoff. The exact transport is a backend decision. Stop unnecessary observation when views are inactive; stopping observation must not stop the job. Thread-grid pagination should not fetch each full history or create one perpetual poller per tile/job. Update bounded thread activity summaries and invalidate affected thread detail/message records instead of walking every thread or conversation array on each event. Queue admission and concurrency/spend limits are server-controlled and configurable; queue position must be omitted or described as approximate unless the scheduler can establish it.

## Accessibility, localization, theming, and performance

Compose existing [Composer](../../../packages/client/src/components/Composer.tsx), [ControlCombobox](../../../packages/client/src/components/ControlCombobox.tsx), [Field](../../../packages/client/src/components/Field.ts), [Slider](../../../packages/client/src/components/Slider.tsx), [Dialog](../../../packages/client/src/components/Dialog.tsx), [EmptyState](../../../packages/client/src/components/EmptyState.tsx), buttons, skeletons, and alerts before adding feature-local styles. The shared Composer already accepts host key policy/Enter behavior and handles IME composition. Media controls should inherit those interaction expectations.

Use semantic theme roles for surfaces, borders, text, focus, and status. Keep studio layout local. A reusable asset selection state or progress presentation can earn a primitive variant or canonical theme token; raw palette classes and copied chat card styles are not a theme system.

All new visible text, status announcements, error mappings, empty states, action labels, and accessible names use `useLocalize()` and English keys in [translation.json](../../../client/src/locales/en/translation.json). Existing hard-coded image labels are not a pattern for new UI. Provider/model names can remain proper names; descriptions and capability labels need localization. Format dates, durations, counts, and available costs with locale-aware formatters.

Use a semantic list styled as a tile grid, or a fully implemented accessible grid, with stable `threadId` keys, named thread-open actions, keyboard-operable menus, and visible focus. Do not nest cancel/download buttons inside the button that opens a tile. Returning from detail restores focus to the originating tile; arriving job events must not steal focus or reorder the reader's current selection. Announce meaningful phase changes, not every progress tick. Videos need labeled native controls, poster/description, no forced autoplay/audio, and captions/transcripts when available. Any later crop/mask canvas needs keyboard-accessible alternatives and labeled controls; do not make an inaccessible canvas the only path to a basic edit. Reduced motion should suppress decorative generation animation without hiding status.

Reserve image/video dimensions and aspect ratios to prevent layout shift. Fetch one bounded cover thumbnail/poster and activity summary per thread tile, load histories/originals on demand, avoid base64 media in React Query/Jotai/DOM state, revoke object URLs, pause offscreen video, and use cursor pagination/virtualization for large thread grids. Opening a thread must not require loading every asset from every thread. Prefer authorized streaming/range-capable delivery for large videos over fetching the entire file into a browser Blob just to play it. Do not cache expiring signed URLs as permanent asset identity.

The studio must not add a blocking catalog/history/job fetch to ordinary chat startup.
